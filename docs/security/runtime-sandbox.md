# Runtime Sandbox Security Contract

This document is the security contract for code generated by ReportAI. It is
intentionally stricter than Docker defaults: a runtime task is untrusted code,
even when it was created by an authenticated tenant.

## Implemented boundary

- The runtime registry accepts only immutable image references in the form
  `repository@sha256:<64 hex characters>`. Mutable tags are rejected during
  application construction.
- A task is rejected before Docker container creation when
  `ExecutionPolicy.networkEnabled` is true. Docker's default bridge is not a
  managed egress policy and must never be treated as one.
- Containers use a non-root UID, drop all Linux capabilities, enable
  `no-new-privileges`, use a read-only root filesystem, disable networking,
  bound PIDs/CPU/memory/output/time, and are removed in a `finally` block.
- When dependencies are required, the Installer writes hash-locked packages
  into a task-scoped volume through the non-root-owned `/home/reportai` parent;
  the Execution container mounts that dependency volume read-only. The
  Installer stages into `/tmp` before copying so pip never performs a
  cross-filesystem rename into the volume.
- Workspace IDs and entry points are allow-listed. Workspaces and their files
  cannot contain symbolic links. Generated artifacts are collected only after
  bounded inspection.
- The scientific profile fails closed when Torch/TorchVision is requested
  without declared real input files or directories. This prevents a model from
  silently substituting synthetic fixtures for a required experiment dataset.
- Environment names are allow-listed and platform loader overrides are
  blocked. Names containing token, password, secret, API key, access key,
  private key, or credential markers are rejected. Secrets must be delivered
  to platform adapters, never to generated programs.

## Managed network work required before enabling egress

Network access must remain fail-closed until a dedicated egress adapter exists.
That adapter must run outside the workload namespace and enforce:

1. explicit tenant, tool and domain allowlists;
2. deny-wins evaluation for overlapping rules;
3. rejection of loopback, link-local, private and metadata-service addresses;
4. DNS rebinding protection by validating the destination at connection time;
5. method and byte budgets, with `GET`, `HEAD` and `OPTIONS` as limited mode;
6. approval for requests outside the declared task capability; and
7. structured audit events with the decision and reason, without query
   strings, headers, source code or secret values.

The boolean in `ExecutionPolicy` is a capability request, not permission to
attach a container to a Docker network. A policy evaluator and managed proxy
must exist before that request can be allowed.

## Filesystem evolution

The current compatibility mount is a bounded read/write workspace. The next
runtime contract should split it into `/workspace/input` (read-only),
`/workspace/output` (read/write), and an ephemeral compiler directory. Artifact
collection will then read only from `output`, preventing generated code from
overwriting the source document or task inputs.

## Evidence required for release

Container CI must archive the digest, UID, capability set, network mode,
no-new-privileges state, mount modes, timeout/output-limit behavior and cleanup
result. A release cannot claim sandbox readiness from unit tests alone.
